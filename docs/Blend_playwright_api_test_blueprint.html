ORIENTATION

HTTP does three different jobs, and mixing them is the first mistake

The useful split isn't UI tests vs API tests. It's the three jobs an HTTP call does inside a suite — each with its own error contract, its own place in the tree, and its own meaning when it fails.

record
The primary business object a test operates on.
member
A sub-entity attached to a record, several per record, with roles.
task
A child resource with a status lifecycle — create, list, transition, delete.
operator
A privileged internal user, created per run and thrown away.
end user
The customer-facing actor who signs in through the public UI.
tenant
One isolated instance of the product; requests route to it by header.
this same picture with the bottom band deleted — which is why the client tier has to exist before you can write either kind well.
JOBWHAT IT ISON NON-2XXA FAILURE MEANS
SEED Build the world the test needs, without a browser. Throw — abort before the assertion runs. Broken environment or credentials, not a product bug.
ORACLE Read back what the UI claims happened; poll async work to a terminal state. Throw, with the response body in the message. Usually a product bug, occasionally a timing assumption.
SUBJECT The contract is the assertion — status codes, response shape, version behaviour, auth rejection. Return it. A 400 is often the expected result. Exactly what the assertion says.

That third row is the one people get wrong. If your only HTTP helper throws on non-2xx, you physically cannot assert a 401 — you end up wrapping every call in try/catch and matching error strings.

STRUCTURE

Four layers, dependencies pointing one way

One rule keeps this maintainable: a lower layer never imports a higher one. A client never imports a page object; config never imports a client. Break it once and your API helpers can't run outside a browser test.

clients can be swept across API versions because transport takes overrides, config can be re-read per call because nothing froze it at import.

DISCOVERY · DO THIS FIRST

Map every access path before you write a client

The expensive mistake is assuming the public API can do everything the UI can. It almost never can. There are usually three write paths into one data model, with different auth roles and genuinely different reach — not layers over one another.

Why seeding stays slow until you find path B. With only A and C, every field outside the public schema has to be typed into a form — that's where ten-minute setups come from. Path B is the one write path a headless service account can use that reaches the same model, and finding it is usually worth more than any other optimisation in the suite.

Finding path B, and the invariants that follow

Perform the action in the UI with the network tab open, note the route the save actually calls, then search the backend for a sibling route with the same reach and an internal or service role — they usually exist for support tooling. Request the scopes early; a missing scope is a 403, which is a provisioning problem, not a payload bug. Internal routes often live on the tenant's own host rather than the API gateway, so derive that host from config.

Internal APIs are permissive in ways that cost you a suite. Write your equivalents of these at the top of the client file:

  • A 2xx is not proof of a write — read the value back and assert it. Some internal APIs accept unknown field ids and discard them.
  • Know the unit and create-marker conventions — dollars vs cents, and whatever flags a new nested collection entry versus an update.
  • Know which objects must not be seeded at all, because a downstream async process only triggers on the real path. Seeding those makes the test green while validating nothing.

Keep the slow path alive as a fallback when internal credentials are absent for an environment, and have the run log say which path it took. A one-word difference in a log line — (api) versus (ui) — saves hours of wondering why a run took twenty minutes.

LAYER 1A

One variable decides host, credentials and tenant

The goal is that a run cannot be half-pointed at two environments. Make one input authoritative and derive everything from it: TEST_ENV enters through dotenv, and three resolvers turn it into an addressed request.

  • Resolve lazily. Wrap config reads in a function called per request. A module-level constant freezes whatever process.env held at first import, which breaks the moment a fixture switches environments between specs.
  • Fail loudly on a missing variable. No default host, no fallback credential — a silent fallback means a green run against the wrong environment.
  • Prefix credentials by environment and select the family by the env key. One getter, not an if per call site.
  • Commit .env.example with every key, empty, one comment each. It's the single most important file for someone replicating the suite.

Watch the secret budget. CI providers cap repository secrets (GitHub: 100). Per-environment × per-service credential families hit that ceiling faster than you expect — plan for grouped secrets or a vault before you're forced into it mid-migration.

LAYERS 1B + 2

Two client layers over the same endpoints

Every resource family gets two sets of functions over the same routes, with deliberately opposite error contracts. createTask(), getTasks(), ensureTask() throw — they serve seeding and oracles, where a failure must abort loudly. createTaskRaw() and friends return { status, body, rawText } and take { version, omitVersion, omitAuth, rawBody } — they serve contract tests, where a 400 is the expected result.

// header builder with test-shaped overrides – this is how you test a 401
function buildHeaders(o: RawOptions = {}) {
  const h = authHeaders();                  // layer 1, resolved per call
  if (o.version !== undefined) h['X-Api-Version'] = o.version;
  if (o.omitVersion) delete h['X-Api-Version'];
  if (o.omitAuth)    delete h['Authorization'];
  return h;
}

// tolerant parser – DELETE returns neither JSON nor a body
async function parseResult(res: APIResponse): Promise {
  const rawText = await res.text();
  let body: unknown = null;
  try { body = rawText ? JSON.parse(rawText) : null; } catch { body = rawText; }
  return { status: res.status(), body, rawText };
}

// the raw call: never throws, always reports
export async function createTaskRaw(args: TaskArgs, o: RawOptions = {}) {
  const ctx = await request.newContext();
  const res = await ctx.post(`${baseUrl()}/tasks`, {
    headers: buildHeaders(o),
    data: o.rawBody ?? composeTaskBody(args),  // rawBody bypasses composition → 400 tests
  });
  const out = await parseResult(res);
  await ctx.dispose();
  return out;
}

Keep composeTaskBody pure so payload shape is unit-testable with no network. rawBody earns its place: without it, "POST with a missing required field returns 400" means either a second client or lying to your type signatures.

Context lifetime is the one real trade-off. A context per call is correct and leak-free but costs a setup per request, which shows when a test sweeps twenty API versions in a loop; the alternative is a client class taking an injected APIRequestContext (Playwright's built-in request fixture works). Pick one per area and be consistent. What's not acceptable is six header builders across six clients — extract that to layer 1 on day one, even with one caller.

Async work needs one poller, not five. Anything returning 202 needs a bounded poll, written once and shared. Two properties make it worth sharing: a terminal-failure predicate, so a job that fails at second 20 fails the test at second 20 rather than at the five-minute timeout, and a label in the error, so a CI timeout tells you which of eleven polls gave up.

await pollUntil({
  poll: () => getOrderStatus(id),  done: s => s === 'SUCCEEDED',
  fail: s => s === 'FAILED' || s === 'CANCELLED',  // abort early
  timeoutMs: 300_000, intervalMs: 5_000, label: `order ${id}`,
});
LAYER 3

Treat seeded state as a lease, not a fresh build

Creating a record costs time and leaves rows in a shared environment. Past a handful of tests, recreating per test is untenable — fixtures cache to disk and hand the same state to everyone who asks. Each spec declares a prefix (test.use({ authPrefix: 'task-contract-suite' })) and the cache path is .auth/{env}/{prefix}/, so two specs never share unless they opt in and a sandbox run never hands state to a staging run.

Write-to-temp, rename, then re-read makes the cross-worker race benign rather than preventing it: whichever rename wins, both workers read the winner, so nothing is orphaned. 
const inflight = new Map<string, Promise<Record>>();

async function ensureRecord(prefix: string) {
  if (inflight.has(prefix)) return inflight.get(prefix)!;       // guard 1: same worker
  const p = (async () => {
    const file = cachePath(prefix);
    if (fs.existsSync(file)) {
      const cached = JSON.parse(fs.readFileSync(file, 'utf-8'));
      if (isUsable(cached)) return cached;                    // validate before trusting
    }
    const created = await createRecord();
    const tmp = `${file}.${process.pid}.tmp`;                 // guard 2: cross worker
    fs.writeFileSync(tmp, JSON.stringify(created, null, 2));
    fs.renameSync(tmp, file);                                 // atomic on POSIX
    return JSON.parse(fs.readFileSync(file, 'utf-8'));        // re-read → converge
  })();
  p.catch(() => inflight.delete(prefix));                    // else one blip is permanent for the worker
  inflight.set(prefix, p);
  return p;
}

Browser storageState lives beside the API cache under the same prefix — the API creates the operator, the first run saves its session, later runs replay it and skip login. Expose variations as fixture options (skipUIFill: [false, { option: true }]) rather than a fixture per shape, and document each option's cache implication: whether state built with the flag is still valid for a run without it.

Cached state accumulates. Anything cleanup can't delete builds up run after run. Document the leak, filter cleanup to what's actually deletable, and say which file to delete to reset. CI should always start with an empty cache directory.

LAYER 4

What the test looks like when the layers are in place

With fixtures leasing state and a raw client that reports rather than throws, a spec carries assertions and nothing else — no beforeAll, no module-level trackers, no helpers defined in the spec file.

test.use({ authPrefix: 'task-contract-suite' });

test('POST /tasks accepts status=OPEN on every supported version', async ({ apiRecord }, testInfo) => {
  testInfo.annotations.push({ type: 'CASE', description: 'TC-1041' });
  const created: Array<{ id: string }> = [];
  try {
    for (const version of ALL_API_VERSIONS) {
      const res = await createTaskRaw({ recordId: apiRecord.id, status: 'OPEN' }, { version });
      expect(res.status, `v${version} — got ${res.status}: ${res.rawText}`).toBe(201);
      assertTaskShape(res.body, { recordId: apiRecord.id, status: 'OPEN' });
      created.push({ id: res.body.id });
    }
  } finally {
    await cleanupTasks(created);       // runs even when a mid-loop assertion fails
  }
});

test('POST /tasks without credentials returns 401', async ({ apiRecord }) => {
  expect((await createTaskRaw({ recordId: apiRecord.id }, { omitAuth: true })).status).toBe(401);
});
  • Every assertion message carries the varying input and the raw response. A matrix failure must be diagnosable from the log alone — expected 201, got 400 is useless when the loop has twenty iterations.
  • Cleanup lives inline in finally, not afterEach, so a mid-loop failure still restores the environment and the list is exactly what this test created.
  • Known bugs get annotated, not hidden. Widen the assertion to an OR-list and attach a BUG annotation naming the ticket — a silently loosened assertion is indistinguishable from a mistake six months later.
  • Matrices come from exported constants in the client, so adding a version widens every suite in one line.

Coverage axes worth writing for each resource family

AXIS CASES
happy pathEach verb, each documented state value, asserting the full response shape rather than just the code.
version matrixEvery supported version. This is where you find silent coercion — an old version accepting a value and storing a different one.
authMissing credentials, wrong credentials, valid credentials without the route's scope. Three codes, three meanings.
malformed inputEmpty body, each required field omitted individually, unknown enum value, well-formed id that doesn't exist.
list semanticsFiltering, empty result (must be [], not 404), missing required query param, pagination boundaries.
lifecycleWhich transitions the API actually permits — probe by sending a bogus value; the validator usually enumerates the allowed set for free.
INTEGRATION

Reporting and CI: API tests ride the same rails

Don't build a parallel reporting path. These are Playwright tests — same report, same selection, same push. Alongside html, allure (which carries your annotations), and json/junit with an env-overridable output path, add one custom reporter: a JSONL writer that appends a line per finished test synchronously in onTestEnd. The built-in JSON reporter only writes at onEnd, so a cancelled or preempted run reports nothing at all; thirty lines of fs.appendFileSync recovers the real partial counts.

Select by tag, not by project. A dedicated api project needs its own testMatch, and a spec that does both jobs then has no home. Give every test a scope tag and a suite tag, and apply @api from day one even with one such test — it's the difference between "run the API suite" being a command and being an archaeology exercise.

npx playwright test --grep @api
npx playwright test --grep "@api" --grep-invert @known-broken
npx playwright test --grep "@regression.*@billing"

The one thing a dedicated project does buy: API-only tests otherwise launch a browser they never use, so a lightweight no-browser project is a real saving on a large matrix.

Traceability wants two mechanisms, both: a case id in the test title (greppable, visible in every report) and the same id as a structured annotation (machine-readable for the push script). Build the results-mapping engine once and give it two front doors — a CI path and a thin local adapter that builds the same input shape from files on disk — never two engines.

REPLICATION

Build it in this order

Each step is verifiable on its own, and each depends on the one before it working.

01

Map the access paths

Before any code. Do the setup action in the UI with the network tab open; identify the public API, the route the UI calls, and any internal admin API. Request the service account and scopes now — provisioning is the long pole.

check: a curl that creates a record end to end
02

Config and credentials

Environment table keyed by one TEST_ENV, lazy host getters, prefixed credential getters, tenant map, committed .env.example. No defaults — a missing variable throws with its own name in the message.

check: a script printing resolved host, tenant and masked creds for two environments
03

Transport

One header builder with overrides, one tolerant parser, one bounded poller with a terminal-failure predicate. ~120 lines; everything imports it.

check: a throwaway test hitting any GET, asserting 200
04

The first resource client

Your central entity: pure body builder, typed helpers that throw, raw helpers that report, version and status matrices exported as constants.

check: create → read back → delete from a node script, no browser
05

The identity factory

A privileged user created and torn down per run. This usually needs an out-of-band channel — an inbox API for an activation link, an SMS provider for an OTP — so budget it as its own component. Deletion is best-effort and unconditional.

check: create → activate → sign in → delete, twice, no residue
06

The caching fixture

Promise map, disk cache under .auth/{env}/{prefix}/, temp-write + rename + re-read, rejection eviction, gitignored. Add the storageState fixtures on the same prefix.

check: same spec twice with 4 workers — second run makes zero create calls
07

The first contract suite

One resource, all six coverage axes, every test tagged @api. This is your template — get the assertion messages, cleanup and annotations right, because everything after is copied from here.

check: green against two environments with only TEST_ENV changed
08

Reporters, CI, then the second area

Wire the reporters and a workflow with environment and tag as inputs. Add the case-id convention and push script. Then clone the area folder for area two — if that clone needs edits below layer 2, your boundaries were wrong, and this is the cheapest moment to find out.

check: a cancelled run still reports finished tests; area two shares layers 1–2 unmodified

Write the conventions file alongside step 7, not later. One markdown per area: which variables it needs, how to run it locally, where each kind of code goes, the cleanup rule, the traceability workflow. It's the difference between a suite one person can extend and one a team can.

FAILURE MODES

The ways this goes wrong

All observable in mature suites; none visible on the day they're introduced.

A header builder per client. Each integration writes its own because it needs one extra header. Later, a platform-wide change is a six-file edit with no compiler help.

Only a throwing client exists. Everything is built for seeding, so the day someone needs to assert a 401 they wrap calls in try/catch and match error strings. Build both layers together even when one has no callers.

Retry and polling reinvented per module. A hardcoded three-attempt loop here, an expect.poll there. Flake fixed in one place teaches the others nothing, and nobody can answer "how long will this wait" globally.

A fork with a documented merge condition that never merges. A shared client hardcodes one environment, so area two copies it with an honest comment explaining what would make the fork unnecessary. The comment ages perfectly; the fork stays. Put the condition on a board, not only in a header.

Example scaffolding outliving its purpose. The demo suite against a public practice API, skipped but still the first thing a newcomer finds when they search for "API test". Delete it once the real pattern exists, or move it under examples/ with a header saying it doesn't run.

No scope tag. Without a consistent @api, the suite can't be scheduled separately from the slow browser matrix. Free on day one, a repo-wide edit by year one.

Cleanup that reports success without succeeding. Some deletes return 2xx and do nothing — a soft delete, or a resource whose only real removal path is the UI. Verify deletion once per resource type while writing the cleanup.

The short version

Keep dependencies pointing one way. Resolve configuration late and loudly. Give every resource two client layers with opposite error contracts. Lease state instead of rebuilding it, and make the cross-worker race benign rather than trying to prevent it. Tag everything. Write the conventions down next to the code that follows them.
